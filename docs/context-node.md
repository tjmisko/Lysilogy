# The context node: why this paper matters

Status: 2026-11-18. Built and tested against stub model backends only. No
live model has answered this prompt yet.

The first view of a paper shows the thesis, the authors' abstract, and then
the account a well-read colleague would give: what question the paper
entered, what it added, and what happened after. The context node writes
that account. It is a judgment call, not an extraction, and it replaces the
disabled web-research design, which withheld every claim that failed web
verification and so was usually empty.

## Where it runs

- **Plan node.** `context` is a feature (`Features::context`) that the reader
  always turns on. In the default pipeline it is a call named `context` with
  the one field `context`. It waits only for the calls that write what it
  reads (identity, type, card, question, relations, references), which is
  `core` in the combined pipeline, so it runs beside the logical-units call.
  `paper_artifacts::run::context_call` builds it.
- **Model and effort.** The call asks for the `strong` tier at high effort
  with a 49k-token output ceiling. The strong tier is the configured
  `analysis.judgment_model` when one is set and the core model otherwise
  (`RunConfig::model_for`). Over the Codex or Claude plan harnesses
  (`Backend::Plan`) the model id is ignored, as for every plan call, and the
  high effort is passed to the CLI (`plan_profile`).
- **App path.** `AnalysisService::analyze_core_artifacts` takes the dossier
  and runs the core plus the context node. `AppState::refresh_component`
  with `AnalysisComponent::Context` (`POST /api/papers/{id}/context/refresh`,
  `lysilogy refresh-context`) runs `run::context_pipeline()`: the context
  call alone over a draft seeded with the core fields of the last run's
  `paper-artifacts.json`, with no self-check. It writes
  `paper-artifacts-context.json` and replaces only the stored context.
- **CLI.** `lysilogy extract --features context` runs the node. A library
  paper gets its dossier from the citation graph; `--dossier file.json`
  supplies one for any PDF, for experiments.

## Inputs

1. The paper's page text, as for every plan call.
2. A brief of the core draft (`context::core_brief`): title, authors, year,
   venue, paper type, question, thesis, position (predecessors, targets,
   replications with their one-line why), relations, and up to 150
   bibliography entries. Quotes are left out.
3. The neighbour dossier (`paper_artifacts::dossier`), rendered as one line
   per work led by its Work id in square brackets.

### The neighbour dossier

Assembled deterministically by `AppState::neighbour_dossier`
(`src/context_dossier.rs`) from what Lysilogy already holds:

- the paper's document row links it to a graph Work;
- `graph.citation_assertion` gives the Works it cites and the Works citing
  it, each with a display title, year and authors;
- `reader.work_prominence` gives worldwide citation counts (from the
  provider payload), local citing counts and a prominence score;
- a neighbour the library holds contributes the abstract and thesis of its
  stored analysis. The graph keeps no abstracts of its own;
- the current citation label on the edge (since 2026-11-18): why the paper
  cites a work, or why a citing work cites the paper, with its relation,
  reason, quote, path, engagement and review state. Rejected labels are
  left out. See `docs/edge-labels.md`.

Each side keeps the 25 most useful titled works: those whose label says
what role they play, then prominence, then worldwide citations, then local
citations, then oldest, then id. The paper's own
counts are given as the subject. A paper with no graph, no Work link, or a
failing query gets an empty dossier; the prompt says so and the node still
runs.

## Output

`prompts/paper-context.schema.json`, generated by
`scripts/spike/build_schemas.py`:

The fields are listed in the order the schema asks for them, which is the
order the model writes them: the lead comes last because it distils the
parts, although the reader shows it first. (`serde_json` is built with
`preserve_order`, so the schema's property order reaches the provider.)

| Field | What it is |
| --- | --- |
| `before` | The state of the question before the paper. |
| `contribution` | What is new relative to `before`. |
| `after` | Who built on it, who disputed it, how it is used now. Empty when unknown. |
| `reception_note` | The model saying it does not know the reception, or null. |
| `read_alongside` | Up to six works the model could cite accurately: `work_id` (dossier id or null), title, authors, year, `relation` (predecessor, successor, critique, replication, survey, parallel), one line of `why`, `basis`. |
| `lead` | Two to four claims, written last: why a smart outsider should care. |

The call is told today's date and the paper's best known year (stated by the
paper, else the graph, else the PDF metadata), so it can tell a paper whose
reception has not happened yet from an obscure one.

The settled context stores the dossier the model read (`context.dossier`:
each work's id, title, year, first author and side, plus whether the graph
could be read), so the reader can name the works dossier claims cite and a
reviewer can check a claim against what the model was given. A refresh whose
context call fails is an error; it never falls back to an older context.

Every claim has `text`, `basis`, `evidence` and `work_ids`. The basis is the
source class:

1. `paper`: the paper says it; `evidence` holds verbatim quotes with pages.
2. `dossier`: a dossier record supports it; `work_ids` names the records.
3. `background`: the model's own knowledge, shown labelled as unverified.

## Settlement

Quotes sit in `evidence` arrays, so the ordinary quote admission checks them
(verbatim, local repair, one model repair, else dropped) and records them in
`ExtractRecord.admission`. Then `context::settle` runs:

- a `paper` claim left with no admitted quote becomes `background` with
  `downgraded: quote_not_found`;
- work ids that are not in the dossier are removed; a `dossier` claim left
  with none becomes `background` with `downgraded: unknown_work`;
- `background` claims are kept, never withheld;
- reading suggestions take their title, year, authors and held paper from
  the dossier record when their id matches; an unknown id becomes null and
  a `dossier` suggestion becomes `background`; duplicates, untitled entries
  and anything past six are dropped.

The counts (`ContextCounts`: dossier size, claims per basis, each kind of
downgrade, unknown ids, dropped suggestions) are stored on the context, on
`ExtractRecord.context`, and a `context_claims_downgraded` warning is raised
when anything was downgraded. The self-check never sees the context, and any
patch it proposes under `/context` becomes a flag.

## In the reader model

- `PaperAnalysis.context: Option<PaperContext>`: the settled answer with its
  counts (serde default; older analyses load as `None`).
- `outsider_brief`: the lead, joined.
- `context_notes`: the before and after claims as `before` and `after` notes
  with `basis` and, for dossier claims, `work_ids` (both serde default).
  Their `source_ids` are empty, so the current Abstract view, which shows
  only URL-verified notes, does not render them yet; wiring the new fields
  into components is the next task.
- `context_sources` is untouched; it belongs to the older web design.
- `web/src/types.ts` mirrors `PaperContext`, `ContextClaim`,
  `ReadAlongside`, `ContextCounts` and `AbstractAgreement`.

## The first-view prompts

`prompts/context.md` explains the reader (intelligent, from another field),
the purpose, what good and bad context look like, the three source classes,
and asks for "not known" over guessed reception. Its worked contrast is from
medicine on purpose, so it cannot leak into an AI or economics paper under
review. The core call's thesis and abstract instructions
(`core_fields::CARD_INSTRUCTION`, `ABSTRACT_INSTRUCTION`) were rewritten in
the same spirit: the thesis states the finding, not the topic; the abstract
is the authors' text exactly, never a summary.

## Abstract cross-check

The deterministic abstract locator still runs. `ExtractRecord` and
`PaperAnalysis` carry `abstract_agreement`: the token F1 between the model's
abstract and the deterministic text (admitted or candidate), with which side
found one and the locator's status. Below 0.8 an `abstract_disagreement`
warning is raised. The F1 matches `scripts/spike/benchmark.py`.

## Not yet known

- Whether a real model follows the source classes, keeps background claims
  honest, and says "not known" when it should.
- How much the dossier helps: most papers in a fresh library are not linked
  to the graph, and the graph's titles are sometimes stubs.
- The cost of a high-effort call on the strong tier per paper.
